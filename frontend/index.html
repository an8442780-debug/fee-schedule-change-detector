Architecture · Equivalence Principle

Consensus-driven row derivation across independent validators

Traditional oracles rely on trusted relays or single-reporter signatures. GenLayer evaluates public web evidence within contract execution and requires independent validator re-checks before a result can settle.

01

Leader normalization

The proposing leader gathers both HTTPS schedules. Responses (capped at 64 KB) are parsed, validated, and normalized into canonical records where service codes are uppercase and billing units are lowercase.

02

Independent re-derivation

Validators do not simply vote on the leader’s output. Under GenLayer’s Equivalence Principle, each validator independently re-checks both URLs, repeats the same normalization logic, and verifies the derivation.

03

Fail-closed finality

Transactions progress through Accepted PENDING → PROPOSING → COMMITTING → REVEALING → ACCEPTED. If upstream sources timeout, return HTTP errors, or validators disagree on normalized results, the contract records UNRESOLVED and refuses to mutate state.

Technical specification: Equivalence principle & validator consensus cycle ↓
Consensus Phase Execution Context Verification Invariant
PENDING Mempool submission Transaction received by the Studionet network; pending recovery journal keeps the hash available.
PROPOSING Elected leader Leader runs _fetch_bundle, executes JSON parse, builds canonical row map, and proposes outcome.

Contract Specification · 8 Outcomes

Deterministic outcome taxonomy for fee schedule comparison

The Intelligent Contract analyzes differences across canonical row keys, billing units, effective dates, amounts, and currencies. Every comparison resolves to exactly one of 8 mutually exclusive contract outcomes.

SAME_SCHEDULE

Identical fee schedules

Both snapshots contain identical canonical rows (service_code, unit) with matching scaled amounts, dates, and currencies. Zero fee divergence detected.

Trigger: Exact row equality across all keys and values
FEE_CHANGED

Amount divergence

Canonical rows match identity, but at least one row has a differing amount_scaled. Persists old_amount and new_amount on-chain (no on-chain delta field; the UI displays the comparison). Amount check precedes date check, winning if both differ.

Trigger: old_amount_scaled != new_amount_scaled (takes precedence over date conflict)
DATE_CONFLICT

Conflicting effective dates

Canonical service codes, units, and amounts match, but effective dates differ between snapshots. Flags uncoordinated timeline changes.

Trigger: old_date != new_date with identical amounts
CURRENCY_CHANGED

Cross-snapshot currency shift

Both snapshots are valid, but Snapshot A currency differs from Snapshot B currency (top-level or per-row). Prevents cross-currency fee comparisons.

Trigger: first.currency != second.currency across valid snapshots
UNIT_CHANGED

Billing unit shift

A service code exists in both schedules but is billed under differing units (e.g. per_request versus per_hour), preventing valid direct amount comparison.

Trigger: Same service code, differing normalized unit
ROW_ADDED

New fee row introduced

Snapshot B introduces one or more canonical rows (service_code, unit) that did not exist in Snapshot A. Represents new service charges or tier additions.

Trigger: Key present in B, absent in A
ROW_REMOVED

Existing fee row deleted

Snapshot A contains canonical rows that are absent in Snapshot B. Represents retired tiers, sunset services, or fee removals.

Trigger: Key present in A, absent in B
UNRESOLVED

Consensus failure or invalid source

Either normalized snapshot is invalid/unavailable (HTTP error, timeout, >64 KB, schema violation), snapshot currency differs from case policy currency, or validators disagree during consensus. Case remains FROZEN.

Trigger: Invalid/unavailable snapshot, policy currency mismatch, or split consensus
Outcome evaluation priority & difference analysis algorithm ↓ 
1. Snapshot Availability & Currency Validation:
   if not first.ok or not second.ok:
       return UNRESOLVED
   if first.currency != second.currency:
       return CURRENCY_CHANGED
   if first.currency != policy_currency:
       return UNRESOLVED

2. Unit Conflict Check:
   if has_unit_conflict(old_codes, new_codes):
       return UNIT_CHANGED

3. Set Difference (Added / Removed Rows):
   if set(new_keys) - set(old_keys):
       return ROW_ADDED
   if set(old_keys) - set(new_keys):
       return ROW_REMOVED

4. Row Currency, Amount & Date Precedence:
   if any(old.currency != new.currency for key in matching_keys):
       return CURRENCY_CHANGED
   if any(old.amount_scaled != new.amount_scaled for key in matching_keys):
       return FEE_CHANGED  # Amount precedes date check; wins if both differ
   if any(old.effective_date != new.effective_date for key in matching_keys):
       return DATE_CONFLICT

5. Exact Equality:
   return SAME_SCHEDULE

Data Integrity · Numeric Safety

Strict decimal-string scaling and zero floating-point arithmetic

Smart contract execution across decentralized nodes requires complete bit-level determinism. Floating-point arithmetic introduces IEEE-754 rounding differences across CPU architectures and is strictly banned.

HTTPS source constraints

  • Endpoints must use the https:// scheme; plaintext HTTP is rejected.
  • URL strings are limited to 256 characters; endpoints must be distinct.
  • Snapshot A and Snapshot B URLs must be strictly distinct.
  • Response bodies are bounded at 64 KB (65,536 bytes).

Canonical row identity

  • Composite primary key: service_code|unit.
  • Service codes are normalized to uppercase and trimmed to 64 characters.
  • Billing units are normalized to lowercase and trimmed to 32 characters.
  • The delimiter character | is rejected inside code or unit fields.
  • Each fee schedule snapshot supports up to 128 rows.

Currency & decimal scale

  • Accepts the explicit supported currency set: USD, EUR, GBP, CAD, AUD, CHF, CNY, INR (scale 2) and JPY, KRW (scale 0).
  • The case form requires the supplied scale to match the supported currency scale (up to 6 decimal places).
  • Arbitrary or unmapped ISO-4217 currency codes are rejected.

String-to-scaled-integer amounts

  • Amounts in JSON are parsed directly from string to integer scaled by 10^scale.
  • E.g. "12.50" with scale 2 maps directly to integer 1250.
  • Amount range is bounded by the contract’s fixed maximum integer value.
  • Zero floating-point operations occur inside contract assessment.

State Machine · Immutable Execution

Deterministic lifecycle transitions: DRAFT → FROZEN → ASSESSED

Cases progress through an intentionally irreversible lifecycle designed to prevent retroactive tampering with evidence windows or fee conclusions.

1. DRAFT

Case initialization

Created by caller with target URLs, currency, and scale. Owner address is sealed. Case parameters cannot be modified after creation.

→
2. FROZEN

Evidence locked

The case owner seals the evidence window. Source URLs are immutable. Ready for validator consensus assessment.

→
3. ASSESSED

Consensus finalized

Validators independently fetch and compare schedules. When consensus resolves, state advances to ASSESSED with final outcome.

Bounded retry path (up to 3 attempts)

When an assessment results in UNRESOLVED (e.g. transient HTTP 503 or network partition), the case remains in FROZEN state rather than failing open. Callers can retry the assessment up to 3 times. Once the retry count reaches 3, further attempts revert.

Pending transaction recovery journal

The frontend maintains an in-browser local storage journal for all submitted transactions. If the browser is refreshed or network interrupts during consensus, the app recovers the pending hash and reconciles the write before permitting any new submission.

Intentionally frozen architecture

The deployed contract contains zero proxy dispatchers, zero delegatecalls, and zero upgrade mechanisms. Its logic is permanent and unchangeable. Verification results are immutable records.

Verified final record

Every displayed case result is read from the settled network state after the transaction reaches finality, so the client never presents speculative validator state as a result.

Interface Specification · Public contract actions

Public actions and access controls

The deployed contract exposes five clearly bounded actions: four writes and one view.

Create a comparison case Public Write

Starts a new comparison case in DRAFT state and records the creating wallet as its owner. Validates HTTPS schemes, limits URL lengths to 256 characters, verifies URL uniqueness, and requires the supplied scale to match the supported currency scale.

Seal the evidence window Owner Write

Locks a case in DRAFT state and transitions it to FROZEN. Only the case owner can seal the evidence window prior to assessment.

Assess the two schedules Public Write

Public action that evaluates a FROZEN case using public web schedules and independent validator re-checks. Normalizes schedule rows, scales amounts to shared integers, analyzes differences according to precedence rules, and updates the case outcome. If resolved, advances state to ASSESSED; if unresolved, remains FROZEN.

Retry an unresolved case Public Write

Public action to re-attempt assessment on any case in FROZEN state with outcome UNRESOLVED. Increments the retry count up to 3; reverts once the retry limit is reached.

Read the verified case record Public View

Returns the complete case record, including owner, state, outcome, URLs, currency, scale, row counts, parsed rows, and evidence digests. Read from the settled network state.

Security Model · Defense-in-Depth

Fail-closed state transitions, owner verification, and zero backend

Architectural security boundaries protecting against injection, state corruption, unauthorized mutations, and false claims of success.

Owner authorization on freeze

Case creation records the creating wallet as owner, and the freeze action strictly enforces owner authorization to seal the evidence window. Once frozen, consensus assessment and retry operations are publicly callable to avoid deadlocking verification.

Prompt & data boundary

Fetched public fee schedules are processed purely as structured JSON data payloads. Raw web text is never concatenated into prompt templates or executed as code, neutralizing prompt injection vectors.

Fail-closed consensus

When upstream data is missing, schema validation fails, or validators disagree, the contract refuses to register an arbitrary outcome. It defaults to UNRESOLVED and holds the state frozen.

Client preflight checks

Before broadcasting transactions, the client verifies the active wallet connection, ensures the selected network is Studionet, checks the available gas balance, and enforces a single active transaction lock.

Safe result rendering

Dynamic case fields, transaction hashes, and error messages are displayed as text-only values. Fetched source content is never treated as markup.

Zero backend footprint

The web application is a pure client-side static bundle. It uses no custodial server and connects directly to the configured Studionet network.
